# Agent Control Plane — спецификация

**Статус:** v3, ждёт ревью владельца.
**Заменяет:** стартовую спецификацию и черновик v2.
**Решения:** [decisions.md](decisions.md). Метки в тексте ссылаются на него: `D` — принято, `O` — открыто. Текст с меткой `O` не реализуется, пока вопрос не решён. Если спецификация и decisions.md расходятся, действует decisions.md.

## 1. Цель

Control plane для долгоживущих агентов на Pi. У каждого агента своя роль, промпт, память, skills и права. Агенты получают триггеры, переписываются асинхронно, вместе работают над задачами, обмениваются файлами и вызывают инструменты под контролем. Всё, что делают агенты, восстанавливается по журналу.

Ценность: система разделяет идентичность, контекст, полномочия и выполнение задачи. Упор — безопасность: минимум прав, изоляция, аудит, секреты вне контекста модели.

Гипотеза H1: Manager работает как attention firewall — фильтрует работу исполнителей и отдаёт оператору результат задачи, а не переписку. Проверяем на dogfooding.

v1 — локальная single-user инсталляция для dogfooding владельцем (облако — O11).

## 2. Принципы

1. Minimal и polished: одна технология на задачу, никаких абстракций про запас.
2. Любое техническое решение, включая crate'ы и форматы, принимает владелец. Открытый вопрос не становится требованием: реализация останавливается на границе и задаёт вопрос.
3. Код — тоже спецификация. Его читают и ревьюят, временные упрощения помечаются комментарием.
4. Идентичность определяется аутентифицированным контекстом, а не данными от модели.
5. Control plane защищается от агентов. Что оператор сознательно выдал агенту, остаётся ответственностью оператора (D18).
6. Компоненты имеют явные границы и не зависят друг от друга (D29).
7. Наблюдаемость встроена с начала.
8. Никаких моковых сценариев в обход настоящих компонентов и никаких скрытых бесконечных ретраев.

## 3. Архитектура

```
 оператор ── CLI (позже UI)          внешние адаптеры (@youtrack, …)
     │ HTTP/JSON                          │ HTTP/JSON
     ▼                                    ▼
┌──────────────────── control plane: один бинарь (Rust) ────────────────────┐
│ Agent Registry   агенты, гранты, коннекторы, проверка токенов             │
│ Tool Gateway     allow/deny для каждого tool call                         │
│ Message Broker   сообщения, inbox, курсоры, решение уведомить             │
│ Task Manager     задачи, статусы, результат, история                      │
│ File Storage     авторизация файлов → S3                                  │
│ Scheduler        расписания → сообщения от @scheduler                     │
│ Agent Memory     записи памяти агентов                                    │
│ Agent Runtime    Run'ы, токены, сессии, статус, лимиты, пробуждения       │
│ Agent Journal    журнал действий агентов (JSONL)                          │
│ MCP-прокси       выданные MCP-серверы, credential (после v1)              │
└──────┬─────────────────────────────────┬──────────────────────┬───────────┘
       │ launcher: stdio JSONL           │ S3                   │ MCP по HTTP
       ▼                                 ▼                      ▼
┌──────────────────────────────┐   ┌──────────────┐   ┌────────────────────┐
│ контейнер на Run             │   │ RustFS (D40) │   │ внешние MCP-серверы│
│ pi --mode rpc                │   └──────────────┘   │ (вендор/оператор)  │
│ + наше расширение:           │                      └────────────────────┘
│   hook tool_call → Gateway   │
│   наши tools → HTTP API      │
└──────────────────────────────┘
```

**Топология v1.** Один бинарь (D20, D44, D28). Каждый компонент — отдельный crate со своей БД: SQLite, файл на компонент (D33). Компоненты общаются через trait'ы с сериализуемыми DTO и явным вызывающим (D11). Crate компонента зависит только от общего `common`, а не от других компонентов, поэтому любой компонент можно вынести в отдельный сервис: его trait реализуется сетевым клиентом, остальной код не меняется (D29). Наружу — JSON поверх HTTP, внутри бинаря — прямые вызовы (D52).

| Компонент | Отвечает за | Не отвечает за |
|---|---|---|
| Registry | агентов, операторов, отправителей-адаптеров, гранты, коннекторы; проверку токенов | запуск агентов |
| Gateway | можно ли этому агенту этот инструмент; пути fs-tools (D39) | предметные проверки сервисов |
| Broker | хранение, адресацию, `allow_message_to`, inbox и курсоры, решение уведомить | способ пробуждения |
| Task Manager | задачи, статусы, подзадачи, результат, историю | сообщения |
| File Storage | авторизацию и метаданные файлов | физическое хранение |
| Scheduler | расписания и отправку сообщений по ним | выполнение Run |
| Memory | записи памяти, поиск, лимиты | что агент запоминает |
| Runtime | Run'ы, токены, сессии, статус агента, лимиты, конфиг Pi на Run | предметную логику |
| Journal | запись и выдачу действий агентов | логи сервисов |
| MCP-прокси | доступ к выданным MCP-серверам, подстановку credential | жизненный цикл MCP-серверов (D63) |

Хранение секретов (credential'ы коннекторов, ключ провайдера модели, credential оператора) — отдельная обязанность со своим требованием: секрет никогда не попадает в среду агента. Реализация — O35.

## 4. Агент

### 4.1. Alias

Alias уникален в пределах инсталляции и используется для адресации, отображения, журнала и прав. У оператора, агентов и отправителей-адаптеров одно пространство alias. Alias оператора задаётся в конфиге, например `@radmir` (D3). Scheduler отправляет сообщения как `@scheduler`, внешний адаптер — под своим alias, например `@youtrack` (D35).

### 4.2. Хранение

Агентов хранит Registry в своей БД. Создаёт и меняет их только оператор, через CLI, позже через UI (D4, D51). Агент не может изменить свой промпт, skills и права.

Перед каждым Run Runtime собирает представление агента в его среде (D51, D59):

| Что | Доступ агента |
|---|---|
| workdir — личный дом агента: его скрипты, скачанные файлы, рабочие копии | read-write, всегда по пути `/work` |
| каталог сессий | read-write |
| промпт, skills, наше расширение | read-only |
| карточка агента, данные других агентов и сервисов | не попадают в среду |

Путь `/work` постоянный, потому что сессия Pi привязана к `cwd` (факт из спайка).

Workdir живёт дольше Run. Это локальный рабочий диск, в отличие от File Storage — общего и долговечного хранилища (§12). Что опубликовать из workdir в File Storage, агент решает сам. Код, с которым работает агент, — git worktree на сессию; как делать это консистентно, решим позже.

### 4.3. Карточка агента

Состав карточки (D69, `connectors` и `limits` появятся позже):

```json
{
  "alias": "coder",
  "title": "Реализует задачи по коду",
  "model": { "provider": "anthropic", "id": "<модель>" },
  "allow_tools": ["read", "write", "edit", "send_message", "read_messages", "get_task", "update_task", "memory_search", "status_set"],
  "allow_message_to": ["manager"],
  "connectors": ["gitlab"],
  "limits": { "max_turns_per_run": 50, "max_tokens_per_run": 200000, "max_wakes_per_hour": 20 }
}
```

Карточка — декларация. Права проверяются при каждом обращении. Числа лимитов в примере условные (O32). Совместимость с A2A не нужна.

### 4.4. Статус

Статус агента хранит Runtime (D60). `status.json` — представление для оператора, в среду агента не попадает. Источники:

1. Runtime: `idle` / `running` / `queued`, `run_id`, задача, время старта.
2. События Pi: текущий инструмент, например «bash: cargo test».
3. Сам агент: `status_set(text)` — через Gateway, с лимитом длины и проверкой на токен.

## 5. Run и Agent Runtime

### 5.1. Жизненный цикл

1. Broker сообщает, что у агента есть непрочитанное (D12).
2. Если у агента идёт Run по той же задаче, Runtime передаёт новое через `steer`. Иначе ставит агента в очередь (D30).
3. Runtime проверяет предохранители (§15), создаёт `run_id` и токен, берёт `correlation_id` из сообщения-триггера (D41), выбирает сессию.
4. Runtime готовит конфиг Pi для Run (§5.4), launcher запускает Pi, Runtime отправляет `prompt` и читает события.
5. На `agent_settled` Runtime закрывает stdin, отзывает токен, двигает курсор inbox (D49), обновляет статус, пишет Journal.

Run записывает свой триггер — `message_id`. `parent_run_id` не храним (D41). Лимитов по времени нет: таймаут Run по умолчанию `None` (D26). Остановка цепочки — `abort` активных Run'ов (D27). Упавший Run — O7.

### 5.2. Один Run на агента и выдача inbox

У агента одно активное Run (D30). Задачи он делает по очереди, каждую в своей сессии. Выдача inbox (D57):

1. Runtime берёт самое старое непрочитанное сообщение агента.
2. Будит агента в сессии задачи этого сообщения.
3. В Run уходят все непрочитанные по этой задаче, остальные ждут следующего Run.

Inbox один на агента, разбор по задачам — фильтр по `task_id`. Это сознательно простой вариант для старта, в коде он помечается комментарием. Сессия для сообщений без задачи — O8.

### 5.3. Сессии

Один Pi-процесс на Run (D43). Сессия — пара «агент + задача», она продолжается в следующем Run через `--session-id` (D14). Промпт и память живут отдельно от сессии.

### 5.4. Запуск Pi

Для каждого Run Runtime создаёт отдельный каталог конфига Pi (`PI_CODING_AGENT_DIR`) с `models.json` и `mcp.json` (D62). В `mcp.json` — только выданные агенту MCP-серверы (D63). Это обязательно: спайк показал, что `--tools` ограничивает только то, что видит модель. Сервер с `exposure: "direct"` запускается, даже если его инструментов нет в `--tools`.

```bash
pi --mode rpc \
  --model <модель агента> \
  --session-dir <каталог сессий> --session-id <сессия> \
  --system-prompt <промпт агента> \
  --append-system-prompt <контекст Run> \
  --tools <грант из Registry> \
  --no-extensions -e <наше расширение> [-e builtin:mcp] \
  --no-skills --skill <skills агента> \
  --no-context-files --no-approve
```

- Контекст Run генерирует Runtime: alias, задача, `correlation_id` (D45).
- Модель видит только инструменты из `--tools` (D22). Gateway — второй слой.
- `builtin:mcp` подключается, только если у агента есть коннекторы. `builtin:codemode` не загружается никогда (D48, D62).
- `--no-approve` запрещает Pi читать `.pi/` из workdir, поэтому агент не может подложить себе настройки или расширения.
- Env процесса — только явный список: токен Run, в первом срезе ключ провайдера модели (D32), переменные отключения сетевой активности Pi. Окружение хоста не наследуется.

### 5.5. Launcher и среда

Launcher — абстракция `start(RunSpec)` → поток stdio и код выхода (D58). Реализации по порядку:

1. локальный процесс — разработка;
2. контейнер на Run — основной режим;
3. эфемерный sandbox — позже (O15).

Расширение общается с control plane только по сети. Runtime и Pi не делят файлы, кроме явно смонтированных.

Образ среды агента — наш, поверх `node:22-slim` по digest: Pi фиксированной версии, непривилегированный пользователь (D61). Firecracker в v1 не используется (D8). Сервисы control plane запускаются через Docker Compose, агент видит только публичный API (D46). Как Runtime запускает контейнеры без `docker.sock` — O14.

| Секрет | Что это | Где находится |
|---|---|---|
| Токен Run | доказывает «это `@coder`, Run r-42» | env Pi-процесса на время Run (D9) |
| Credential оператора | доказывает оператора | у CLI оператора; хранение — O35 |
| Credential адаптера | доказывает внешний адаптер, например `@youtrack` | у адаптера; хранение — O35 |
| Ключ провайдера модели | API-ключ Anthropic, OpenAI и т. п. | первый срез — env (D32), дальше — O22 |
| Credential'ы коннекторов | токен GitLab, SSH-ключ | только control plane, подставляет MCP-прокси (D63) |

**Токен Run** (D9, D24):

- префикс `sona_plane_rt_` и случайная часть, в БД хранится только хэш;
- выпускает и проверяет Registry по запросу Runtime (D68);
- живёт ровно столько, сколько его Run: TTL нет, отзыв по концу Run, при старте сервера отзываются все токены Run;
- расширение подставляет его в заголовки, модель не передаёт его в аргументах;
- с bash модель может его прочитать, это допустимо (D21). Главное — токен не уходит за пределы агента: Broker, Task Manager и File Storage отклоняют содержимое с активным токеном и пишут это в Journal;
- позже — привязка токена к среде агента.

Запрещено класть секреты в промпт, сообщения, задачи, память и Journal.

## 7. Tool Gateway

На `tool_call` наше расширение приостанавливает вызов и передаёт Gateway токен, инструмент и пути для fs-tools. Gateway проверяет грант из Registry и пути: сначала `realpath`, потом сравнение с разрешёнными каталогами (D39). Решение пишется в Journal, на deny вызов блокируется с причиной, и модель видит её как ошибочный результат.

Контроль распространяется на встроенные, наши и MCP tools: спайк подтвердил, что hook видит и блокирует все три вида.

- Встроенные fs-tools работают только в workdir (D2). Исключение — `read` в skills (D59).
- Если Gateway недоступен, вызов блокируется (D38). Если hook упал, Pi блокирует вызов сам.
- Bash выдаётся только по гранту и работает внутри контейнера агента (D21).
- Предметные проверки остаются в сервисах.

## 8. Инструменты и коннекторы

**Наши инструменты v1** (названия не окончательные):

| Группа | Инструменты |
|---|---|
| Сообщения | `send_message`, `read_messages` |
| Задачи | `create_task`, `get_task`, `update_task` |
| Файлы | `put_file`, `get_file`, `list_files` |
| Память | `memory_add`, `memory_list`, `memory_search`, `memory_delete` |
| Статус | `status_set` |

**Коннекторы.** Коннектор — внешняя возможность: MCP-сервер, SSH, пользовательский код. У него три части: capability (что можно делать), scope (над чем) и credential (секрет, только у control plane). Оператор объявляет коннектор в Registry и выдаёт агенту гранты. Опасные коннекторы, включая SSH, выдаются явно, на ответственность оператора (D18).

**MCP** (D63):

- MCP-серверы внешние — у вендора или запущенные оператором. Core их только подключает и не управляет их жизненным циклом.
- В `mcp.json` агента — только выданные ему серверы, каждый отдельной записью.
- URL записи ведёт на наш MCP-прокси (`/mcp/<коннектор>`) с токеном Run. Прокси проверяет грант, подставляет credential, пересылает вызов и пишет его в Journal.

Транспорт пользовательского кода, контракт ошибок, scope и политика внешних действий — O10. Progressive disclosure инструментов — O33.

## 9. Message Broker

Коммуникация асинхронная, как email. Групповых чатов, broadcast и CC в v1 нет.

```text
id
from            # ставит Broker по токену
to              # существующий alias
body
created_at      # ставит Broker
in_reply_to     # nullable
task_id         # nullable
subject         # optional
correlation_id  # ставит Broker, всегда заполнено (D41)
```

Правила:

- Broker проверяет, что `to` есть в `allow_message_to` отправителя (D50).
- Получатель получает короткое уведомление без тела: `<new_message from="@coder" />` или `<new_messages count="2" />`.
- Broker решает, что надо уведомить. Runtime решает, как: новый Run или `steer` (D12).
- Уведомление — подсказка, источник истины — inbox. При старте Runtime спрашивает непрочитанное и будит агентов (D15). Outbox не делаем.
- Курсор inbox — на сессию. `read_messages` его не двигает. Успешный Run двигает курсор до последнего выданного сообщения, после падения сообщения выдаются снова (D49).
- Сообщения в остановленную цепочку сохраняются, но никого не будят (D27).

Гарантия — at-least-once. Exactly-once не заявляем. Дедупликации нет: повторная отправка создаёт второе сообщение (D10). Размеры, retention и приоритеты — O26.

**Триггеры** — обычные сообщения (D35). Оператор, `@scheduler` и внешние адаптеры отправляют их так же, как агенты, через тот же API и те же проверки.

## 10. Task Manager

Задача (D53):

```text
task_id
title, context
status          # open → in_progress → done / cancelled, плюс needs_owner
creator, created_at
assignee        # nullable: один ответственный, двигает задачу дальше
members         # остальные агенты, работающие над задачей
parent_id       # nullable: подзадачи
deadline        # nullable, по умолчанию None (D26)
result          # текст и ссылки; файлы — в пространстве задачи (D56)
history         # append-only: when, who, what
```

- Видят задачу и пишут в неё участники — создатель, `assignee`, `members` — и оператор (D72).
- Автора и время записей ставит Task Manager по токену.
- `done` и `cancelled` ставят только создатель или оператор: задачу создаёт Manager, он её и закрывает. Закрытая задача не меняется.
- Задача сама не будит агентов, будят сообщения.
- `needs_owner` — задача ждёт решения оператора. Когда Manager к нему обращается — O29.

Как оператор видит задачи («в работе / завершено / ждёт тебя» с результатом) — O30.

## 11. Память

Память — записи, а не файл (D31). Целиком в промпт не подставляется: агент сам «вспоминает» через поиск (D16).

- Инструменты: `memory_add`, `memory_list`, `memory_search`, `memory_delete`.
- Запись хранит текст, `run_id`, `correlation_id`, время, позже taint-метку. По этим полям можно найти и удалить запись, закреплённую prompt injection.
- Лимит объёма: при превышении `memory_add` возвращает ошибку, и агент сам решает, что удалить.
- `memory.md` — представление памяти для оператора.

Числа лимитов и устройство поиска — O19.

## 12. File Storage

Наш сервис авторизует запросы по токену и проксирует их в S3-совместимый backend через `rust-s3` (D5). Backend — RustFS (D40). Знание пути не даёт доступа, публичного доступа нет, содержимое файлов не пишется в журнал.

Пространства и права (D56):

| Пространство | Доступ |
|---|---|
| `agents/<alias>/…` | сам агент, read-write |
| `tasks/<task_id>/…` | участники задачи: создатель и исполнители, read-write; сюда же кладётся результат |
| вложение в сообщение | получатель, чтение этого файла |
| всё | оператор |

Права выводятся из структуры, списков ACL в v1 нет.

## 13. Scheduler

Отдельный компонент со своей реализацией (D6). Расписания хранятся в его БД, cron-выражения разбирает `croner` (D19). Цикл спит до ближайшего срабатывания, отправляет сообщение от `@scheduler` (D35) и сохраняет `last_fired_at`. Перекрытия, пропуски и часовые пояса — O25. Самопланирование агентов не добавляем.

## 14. Agent Journal и логи

**Agent Journal** — только действия агентов, как auditd (D13). JSONL-файлы с ротацией, один писатель (D17). Строка (D42):

```text
timestamp, actor, component, action, decision, result, reason, run_id, correlation_id, task_id
```

- Gateway пишет попытку и решение.
- Runtime пишет жизненный цикл Run и `ok/error` из `tool_execution_end`.
- MCP-прокси пишет вызовы коннекторов.
- Аргументы и результаты инструментов не сохраняются.

**Логи сервисов** (`tracing`) — отладка и подробности. Переписка хранится в Broker и его логах.

Историю восстанавливают, связывая Journal и данные сервисов по `run_id` и `correlation_id`. Credentials нигде не записываются.

**Стоимость.** В сессии Pi у каждого ответа модели есть `usage` и `cost`. Учёт по агенту, задаче и Run — O28.

## 15. Предохранители и безопасность

**Циклы** (D37):

- лимит Run'ов на `correlation_id`;
- лимит глубины `in_reply_to`;
- лимит ходов и токенов на Run;
- лимит пробуждений агента за окно.

Числа — O32, детектор циклов — после v1. Оператор останавливает цепочку командой: активные Run'ы прерываются, новые пробуждения по её `correlation_id` запрещаются (D27).

**Prompt injection.** Полной защиты нет, поэтому ограничиваем последствия. v1 (D50):

- минимум прав по ролям: агент, читающий недоверенные данные, не получает опасных инструментов и коннекторов. Текст от внешних адаптеров всегда недоверенный, например описание issue, поэтому адаптер пишет только агентам с минимальными правами;
- список адресатов `allow_message_to`;
- агент не может изменить свой промпт, skills и права;
- память атрибутирована, закреплённую инъекцию можно найти и удалить (§11).

После v1 (D23, O16): taint-метка на Run и сообщения, которая ставится сервером и ужесточает права; подтверждение оператора для опасных действий; ограничение исходящей сети.

**Изоляция.** Hook — не граница безопасности на уровне ОС, у Pi нет своей песочницы. Граница — контейнер на Run, монтирование по §4.2 и сеть, в которой агенту доступен только наш API (D46).

## 16. Внешний API

Клиенты — наше расширение, CLI оператора и внешние адаптеры. Формат — JSON поверх HTTP (D52). Каждый запрос авторизуется: токеном Run, credential'ом оператора или адаптера. Вызывающего определяет сервис, а не тело запроса. Внутри бинаря сетевых вызовов нет.

## 17. Репозиторий и код

Cargo workspace `control-plane` (D36), каталог crate'а — `crates/<компонент>`, пакет — `control-plane-<компонент>`. Состав и стек — раздел «Стек» в decisions.md (D55). Pi-расширение — TypeScript в `extension/` (D1). Ветка `master` — основная, `dev` — рабочая.

## 18. Тестирование

Сквозные тесты гоняют настоящий Pi с заглушкой модели: OpenAI-совместимым сервером, который отвечает заданными по сценарию tool calls. Pi направляется на неё через `baseUrl` в `models.json` (D25). Настоящая модель — только в ручном smoke-тесте. Негативные сценарии из §19 покрываются автотестами.

## 19. Сквозной сценарий v1

Участники: `@manager`, `@coder`, оператор.

1. Оператор создаёт задачу и пишет `@manager`.
2. Manager пишет `@coder` со ссылкой на `task_id`.
3. Broker сохраняет сообщение и сообщает Runtime, что у Coder есть непрочитанное.
4. Runtime запускает Coder в сессии этой задачи, тот получает уведомление без тела.
5. Coder читает сообщение и задачу, обновляет задачу.
6. Coder кладёт результат в файлы задачи.
7. Coder пишет Manager. Manager просыпается в той же цепочке, проверяет результат и завершает задачу.
8. Все tool calls прошли через hook и Gateway, Journal показывает историю по `correlation_id`.

**Негативные сценарии:**

- Запрещённый инструмент не исполняется, попытка и причина есть в Journal.
- Fs-tool с путём вне разрешённых каталогов блокируется.
- Сообщение адресату вне `allow_message_to` отклоняется.
- Подделанный `from` не меняет отправителя.
- Сообщение с активным токеном Run отклоняется.
- Цикл между агентами останавливается предохранителем.
- Run упал после чтения сообщения: при следующем запуске сообщение выдаётся снова.
- Остановленная цепочка никого не будит.

## 20. Критерии приёмки

- [ ] Manager и Coder созданы через CLI, alias уникален.
- [ ] Runtime запускает Pi в контейнере с промптом, skills, грантом и конфигом на Run.
- [ ] Broker принимает, хранит и выдаёт сообщения; тело не входит в уведомление.
- [ ] Новое сообщение будит агента; сверка inbox работает после рестарта.
- [ ] Сообщение по задаче активного Run доставляется через `steer`.
- [ ] Task Manager хранит статус, подзадачи, результат и append-only историю.
- [ ] Автор сообщений и записей определяется сервисом.
- [ ] File Storage требует авторизацию и соблюдает пространства.
- [ ] Scheduler отправляет сообщение выбранному агенту.
- [ ] Hook перехватывает встроенные, наши и MCP tools.
- [ ] Запрещённый вызов не исполняется и журналируется, результат исполненного журналируется.
- [ ] Credentials не попадают в промпт, сообщения, задачи, память и Journal.
- [ ] Сквозной сценарий проходит из чистого запуска по документированной инструкции.
- [ ] Негативные сценарии покрыты автотестами с заглушкой модели.
